# DOCUMENTACIÓN OFICIAL QPAYPRO API (base de conocimiento del agente)

## 1. AUTENTICACIÓN
Todos los recursos se autentican con claves de un comercio. Las claves que deben reemplazarse en producción
por las credenciales entregadas al registrarse como comercio son:
- x_login          -> identifica al comercio. Sandbox: visanetgt_qpay. En producción es la PUBLIC_KEY del comercio.
- x_private_key    -> llave privada del comercio. Sandbox: 88888888888
- x_api_secret     -> llave identificadora de la transacción API. Sandbox: 99999999999
En el checkout alojado la llave privada viaja como x_api_key (sandbox: 88888888888).
En QpayFel la autenticación se hace con el campo public_key.
Las credenciales viajan SIEMPRE en el body de la petición, nunca en cabeceras.

## 3. APP CHECKOUT PAGE (página de pago alojada)
Proceso general:
1. Tu sistema envía la información del cliente y carrito para generar un token de transacción (no datos de tarjeta).
2. QPayPro almacena la información y genera el token.
3. Tu sistema construye la URL de pago con ese token.
4. QPayPro retorna la confirmación a la URL de éxito configurada en el comercio.

### Código HTTP 422 (responseCode 1003)
Significa que la transacción tiene definida la pasarela de pago BAC y requiere autenticación 3D-Secure.
Debe seguirse la documentación de pagos 3DS BAC.
{
  "result": 0,
  "title": "Error",
  "responseCode": "1003",
  "responseText": "La transacción tiene definida la pasarela de pago BAC ... requiere 3D-Secure",
  "redirect": null,
  "forceRedirect": false
}

## 5. PAGOS 3DS BAC
Mismo endpoint que procesar pago (/checkout/api_v1). Agrega el objeto payment_response_url cuando el comercio
recibe pagos con AMEX y tarjetas BAC:
"payment_response_url": { "success_url": "https://midominio.com/success", "error_url": "https://midominio.com/error" }
Ambas URL son de tipo GET.
Al detectar doble autenticación el servicio devuelve HTTP 303. Se debe leer responseObjectBac y redirigir:
window.location.href = response.responseObject.responseObjectBac.redirect;

## 6. FLUJO 3DS2 (CyberSource)
Pasos:
1. Iniciar pago: POST /checkout/api_v1 con el payload completo. Si result: 1 el flujo termina aquí.
2. Si la respuesta incluye responseObject3ds.step2CreateIframe (referenceId, deviceDataCollectionUrl,
   accessToken) hay que ejecutar el Device Data Collection SOLO en frontend: form POST al
   deviceDataCollectionUrl dentro de un iframe oculto.
3. Continuar autenticación: POST /checkout/api_v1 con el payload original más
   "cybs3ds": { "reference_id": "{{referenceId}}", "continue_auth": true }
4. Si la respuesta incluye step4CreateIframeChallenge (stepUpUrl, accessToken) hay que mostrar el challenge en un
   iframe/modal en frontend: form POST a stepUpUrl con JWT=accessToken.
5. Continuar después del challenge: POST /checkout/api_v1 con el payload original más
   "cybs3ds": { "transaction_id": "{{transactionId}}", "continue_payment_after_challenge": true }
6. Confirmación final: result: 1 o status: AUTHORIZED significa pago exitoso.
   { "result": 1, "title": "Éxito", "responseCode": 100, "responseText": "Transacción exitosa",
     "responseAuthorization": "831000", "idTransaction": 422492 }

Variables de entorno del frontend:
window.APP_ENV = 'sandbox';
window.CYBS_3DS_CENTINEL_CARDINALCOMMERCE_TEST = 'https://centinelapistag.cardinalcommerce.com';
window.CYBS_3DS_CENTINEL_CARDINALCOMMERCE = 'https://centinelapi.cardinalcommerce.com';
window.APP_PAYMENTS = 'https://sandboxpayments.qpaypro.com/checkout/';
BACKEND_URL = 'https://api-sandboxpayments.qpaypro.com/checkout/api_v1';

## 7. TOKENIZATION (QPayToken)
Permite almacenar tarjetas de forma segura mediante tokens para agilizar el checkout.
Primero se registra el cliente, luego se asocia la tarjeta (token) y después se cobra con el token.

### POST registrar cliente
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/create_user_client_token_validations
Requeridos: x_login, x_private_key, x_api_secret, x_first_name, x_last_name, x_address, x_city, x_state,
x_zip, x_country, x_email.

### PUT modificar cliente (solo si no tiene token asociado)
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/user_client_token/update
Header Accept: application/json. Requeridos: credenciales + x_user_client_id. Resto de campos opcionales.

### POST listar clientes
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/user_client_token/list
Header Accept: application/json. Solo credenciales.

### POST buscar clientes
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/user_client_token/find
Filtros: user_client_id, first_name, last_name, street, city, state, zip, country, email.

### POST registrar token (asociar tarjeta)
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/associate_card_token_user_validations
Requeridos: x_login, x_private_key, x_api_secret, user_client_id, cc_number, x_exp_month, x_exp_year,
x_card_type (001 = VISA, 002 = MASTERCARD), cc_cvv2.

### POST eliminar token
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/delete_token_validations
Requeridos: credenciales + x_token_user.

### POST procesar pago por token
https://api-sandboxpayments.qpaypro.com/checkout/tokenization/process_payment_token_client_validations
Requeridos: credenciales + x_token_user. Opcionales: x_currency (GTQ o USD), x_amount (decimal, ej. 1.10).
{
  "x_login": "visanetgt_qpay",
  "x_private_key": "88888888888",
  "x_api_secret": "99999999999",
  "x_token_user": "6692458385676837804011",
  "x_currency": "USD",
  "x_amount": "1.02"
}

https://api-payments.qpaypro.com/checkout/qpayfel/anular/factura

## 9. COBROS AUTOMÁTICOS / SUSCRIPCIONES (billing)
Base: https://api.qpaypro.com
Autenticación en el body con x_login, x_private_key, x_api_secret.
Credenciales de prueba: x_login 5gNwBPoqmft16860, x_private_key O1gn8SgILKV16860, x_api_secret DCCyMKKSpqG16860.
Las credenciales del comercio se consultan en la plataforma en la ruta /integrations.

### Clientes
- POST   /billing/user-clients/create  -> first_name, last_name, street1, city, state, zip, country (opcional,
         default "Guatemala"), email, telefono, nit, identification_user.
- PUT    /billing/user-clients/{id}    -> solo los campos a modificar.
- DELETE /billing/user-clients/{id}
- POST   /billing/user-clients         -> listar
- POST   /billing/user-clients/{id}    -> ver por id

### Productos
- POST   /billing/products/create -> name, description, currency (GTQ|USD), precio, recurrencia, short_description, sku.
- PUT    /billing/products/{id}
- DELETE /billing/products/{id}
- POST   /billing/products        -> listar
- POST   /billing/products/{id}   -> ver

### Tokenización de tarjetas (billing)
- POST /billing/associate_credit_card -> user_client_id, cc_number, x_exp_month, x_exp_year,
        x_card_type (001 VISA, 002 MASTERCARD), cc_cvv2, origin (ej. API_SUSCRIPCIONES). Devuelve el token_id.
- POST /billing/process_token_payment -> token, currency, amount, origin. Cobro inmediato.
- POST /billing/list_credit_card      -> x_client_id. Un cliente puede tener varias tarjetas, cada una con su token_id.
- POST /billing/delete_credit_card    -> x_client_id, cc_id.

### Suscripciones
- POST /billing/subscriptions/create -> customer_id, product_id, token_id, currency, ciclos (requerido),
        plan_description, facturar (0 No / 1 Sí), CUI-NIT (obligatorio si facturar=1).
- POST /billing/subscriptions/{id}          -> detalle
- PUT  /billing/subscriptions/{id}          -> actualizar precio, next_billing_date, recurrencia, status, token, email
- POST /billing/subscriptions                -> listar todas
- POST /billing/subscriptions/{id}/invoices  -> comprobantes

Estados de suscripción: 0 = Cancelada, 1 = Activa (default), 2 = Pausada.
Estados de factura/comprobante: 1 = Pagada, 2 = Pendiente, 3 = Vencida.
Campos del comprobante: invoice_number, invoice_date, total_invoice, currency, status, description, transaction_id.

Recurrencias soportadas: diario/diaria, semanal, quincenal/quincena, mensual/mes.
Cálculo de end_date con ciclos:
- Diario:     start_date + ciclos días
- Semanal:    start_date + (ciclos x 7) días
- Quincenal:  start_date + (ciclos x 15) días
- Mensual:    start_date + (ciclos x 30) días
Si no se especifica end_date ni ciclos la suscripción es indefinida. Cada suscripción maneja una sola recurrencia.

Cobro automático: al llegar next_billing_date se intenta el pago con el token_id. Si es exitoso se crea un
comprobante, sube billing_count y se actualiza next_billing_date. Si falla sube fail_count_billing; al tercer
intento fallido la suscripción se pausa. billing_activation_date es la fecha en que arranca la facturación
automática (default: fecha actual). plan_total es el monto que se cobra en cada ciclo.

Facturación con INFILE: el sistema prepara los datos al crear la suscripción con facturar=1, pero la factura
electrónica se emite durante el cobro recurrente. Requiere INFILE habilitado por soporte.

## 10. ERRORES COMUNES
- HTTP 503 "Base de datos deshabilitada": servicio no disponible, contactar a soporte.
- "Credenciales inválidas": revisar x_login, x_private_key y x_api_secret (sin espacios ni caracteres extra).
- "Cliente no encontrado para este business": el customer_id no existe o no pertenece al comercio.
- "Producto no encontrado para este business": el product_id no existe o no pertenece al comercio.
- "Token no pertenece al cliente o no existe": el token_id no existe, no está asociado a ese customer_id
  o no pertenece al comercio.
- "Recurrencia no soportada para calcular end_date": usar diario, diaria, semanal, quincenal, quincena, mensual o mes.
- "Debe enviar CUI-NIT cuando facturar=1": falta el campo CUI-NIT (o cui_nit).
- "El comercio no tiene INFILE habilitado para facturar": solicitar habilitación a soporte.
- "Error al conectar con pasarela": problema de conectividad con el servicio de pagos.
- HTTP 422 responseCode 1003: la pasarela BAC exige 3D-Secure; seguir el flujo de pagos 3DS BAC.
- HTTP 303: el banco pide doble autenticación; redirigir a responseObject.responseObjectBac.redirect.

Comportamiento observado en el sandbox (comprobado con peticiones reales; no figura en la
documentación oficial de QPayPro):
- HTTP 400 con {"result": 0, "responseText": "x_login inactive or does not exists"}: alguna credencial
  no es válida. La API de pagos devuelve el mismo mensaje sin importar si falla x_login, x_private_key o
  x_api_secret, así que hay que revisar las tres. Sin credenciales responde "x_login is required".
- HTTP 502 Bad Gateway: el sandbox lo devuelve de forma INTERMITENTE, incluso con peticiones válidas (la
  misma llamada puede dar 200 y segundos después 502). NO significa que la petición o las credenciales
  estén mal; hay que reintentar tras unos segundos. La respuesta es una página HTML de nginx, no JSON:
  la integración debe revisar el código HTTP antes de parsear el cuerpo, o fallará con un error de JSON.
